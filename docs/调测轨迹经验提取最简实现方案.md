# 调测轨迹经验提取最简实现方案

## 1. 目标与实现依据

在现有 memory 服务中增加定时任务：查询调测 Step、聚合完整轨迹、提取有效修复经验，并写入现有经验中心。

本方案基于业务确认及本地 Agent 提供的代码仓分析；文件路径为目标 memory 仓库的实施建议，实施时核对实际函数签名。业务格式参考 [调测轨迹经验提取最简方案](./调测轨迹经验提取最简方案.md)，接口契约参考 [经验管理 API 文档](./经验管理%20API%20文档.md)。

已确认的运行条件：

- 服务负责人保证当前及后续仅部署一个服务实例，只有一个 task_runner 执行本任务。
- 定时周期可配置，初版每天执行一次。
- 本轮完成后才调度下一轮；手动补跑前暂停定时任务并等待当前轮结束。
- 不增加 SQL 任务锁、Redis 锁、租约或游标乐观锁。
- ES 保存经验正文及检索字段；现有 SQL 数据库保存游标和处理状态。
- 复用现有模型调用、经验向量化、版本归档和质量检测。

## 2. 经验粒度与数据来源

### 2.1 经验粒度

一条轨迹中的一个有效修复点，对应一个与修改直接关联的主失败现象，生成一条经验。

- 轨迹通过源数据的 case_id + test_user 查询全部 Step。
- 一条轨迹可输出多条经验。
- 不同轨迹中相似的失败现象分别录入，不做跨轨迹合并。
- 以 fix_result 表示“修复有效”为有效性依据；具体接口枚举通过配置映射，例如样例中的 success。
- 同时要求存在实际修改，并能关联主失败现象。
- 无成功修复不入库；只增加诊断而未解决原故障的修改不入库。
- 正文保持 Debug Trace、Error Log、Diff、Root Cause、Pattern 五段式。

### 2.2 外部接口

使用接口方正在提供的两项能力：

| 接口能力 | 用途 |
| --- | --- |
| update_time + id 联合游标分页查询 | 发现新增或更新的 Step |
| case_id + test_user 全历史分页查询 | 获取完整轨迹 |

必须读取全部结果状态，不能在增量接口仅筛选修复有效，否则无法发现有效结果被撤销。

现有 test_case_steps5 及仅按 case_id 查询的接口，不能直接替代这两个外部接口，因为其模型缺少本需求字段。

调用轨迹查询时保留源 test_user 原值及匹配语义；仅在云见 user_id 映射时将空值转换为字符串 "0"，不能把查询条件中的空用户直接替换成 "0"。类似 "no user" 的占位值按最终接口约定处理。

## 3. 最小模块改动

| 文件（目标 memory 仓库） | 改动 |
| --- | --- |
| memory_service/trace_experience_pipeline.py（新增） | 数据客户端、轨迹编排、模型提取、经验同步及 run_once 入口 |
| project_configs/prompt_configs.py | 增加 TRACE_EXPERIENCE_PROMPT |
| project_configs/settings.py | 增加数据接口、调度、试运行和模型预算配置 |
| db_operate/sql_models.py | 新增游标表和轨迹处理记录表 |
| db_operate/sql_operator.py | 增加状态读写及待重试记录查询 |
| task_runner.py | 注册任务，等待一轮结束再安排下一轮 |
| api/experience_api.py、memory_service/experience_manage.py | 如尚无独立业务函数，最小抽取经验创建/覆盖及删除逻辑，供路由和任务共用 |
| test/experience/test_trace_experience_pipeline.py（新增） | 覆盖提取、重试、更新和失效删除 |

新增管道放在 memory_service 下，与经验业务归属一致。不改造旧 Step 索引，不新增通用 HTTP 框架或任务队列。

复用 LLMCaller、现有 JSON 解析方式和日志组件。模型调用与 HTTP 访问若为同步阻塞函数，通过现有线程机制或 asyncio.to_thread 执行，避免阻塞 task_runner 中其他任务。

## 4. 执行流程

1. 读取待重试轨迹，优先处理；失败项保留，下次重试。
2. 读取当前运行范围对应的增量游标。
3. 分页获取新增或更新的 Step。
4. 按源 case_id + test_user 去重；将每组写成 pending 处理记录。
5. 调用全历史接口，取得完整轨迹并稳定排序。
6. 按产品范围分开分析，避免一个返回组合中混入不同 group_id。
7. 计算规范化轨迹内容摘要；与已成功处理版本一致时跳过。
8. 对已知经验先检查其修复结果是否已明确失效，并同步删除。
9. 正常轨迹调用一次大模型，输出多个候选；超长轨迹按第 6 节处理。
10. 校验候选来源及内容，组装五段式 Markdown，创建或覆盖经验。
11. 记录成功的输入摘要、来源修复点与 doc_id 对应关系。
12. 当前页全部成功、正常跳过，或已持久化为待重试后，推进页尾游标。

获取增量页失败、处理记录无法落库时，不推进游标。重试记录必须独立于全局游标被再次扫描，防止游标推进后遗漏失败轨迹。

## 5. 两张最小 SQL 状态表

### 5.1 游标表 trace_experience_job_state

| 字段 | 用途 |
| --- | --- |
| job_name（主键） | 区分试运行、历史补跑、正式增量 |
| range_start、range_end | 本轮查询范围，采用左闭右开区间 |
| last_update_time、last_id | 已安全处理的增量位置 |
| updated_at | 状态更新时间 |

范围变更时新建或显式初始化对应任务状态，不静默复用旧范围游标。表中不增加锁字段。

### 5.2 轨迹记录表 trace_experience_record

| 字段 | 用途 |
| --- | --- |
| trace_key（唯一键） | 按来源 case_id + 原始 test_user 构造稳定键 |
| case_id、source_test_user | 重试时重新获取完整轨迹；保留空值语义 |
| processed_trace_hash | 最近成功处理的轨迹摘要 |
| source_update_time | 本次源数据更新时间 |
| experience_refs | 各 group_id、fix_step_id、doc_id 及已写入内容摘要的对应列表 |
| process_status | pending / success / skipped / failed |
| retry_count、last_error | 重试与诊断 |
| created_at、updated_at | 处理时间 |

列表采用现有数据库支持的 JSON 或序列化文本保存。以轨迹为状态单位，可以记录“轨迹接口尚未成功，因而还不知道 fix_step_id”的失败；一条记录支持多条经验。

新表遵循现有 SQLAlchemy 建表方式，并确保首次任务访问前已完成初始化。不能假定 server.py 与 task_runner.py 同时启动时建表一定先完成。

## 6. 大模型提取

### 6.1 正常轨迹

输入按 start_time、end_time、update_time、id 排序的完整 Step，并提供允许提取的有效修复 Step ID。无有效候选时跳过模型，但仍执行已有经验的明确失效清理。

模型输出 JSON 数组，每项包含：

- fix_step_id、related_step_ids；
- valid、reason；
- failure_phenomenon、title、summary；
- debug_trace、error_log、diff、root_cause、pattern；
- rag_search_text。

程序校验 fix_step_id 和 related_step_ids 均来自当前输入，修复点状态有效、hasChanged 为 true、changedLines 非空，且 fix_step_id 无重复。

标题采用“主语 + 核心失败表现”。Diff 只保留关联改动；没有来源文件路径时标注“源数据未提供文件路径”，不编造文件名。修复结果只提供有效性判定时，写“fix_result 判定修复有效”，不擅自写成整条用例执行通过。

### 6.2 超大轨迹

- 根据模型上下文及输出预算判断是否超长。
- 按有效修复点组织关联失败、修改、验证片段，分批提取。
- 保留 Step ID、时间顺序、核心错误和完整关联 Diff。
- 无法可靠确定关联范围时记录失败并重试或人工定位，不猜测关联。
- 单个修复片段仍超长时，记录超限原因；不静默截断必要证据。
- 任一分批结果失败，不将整条轨迹标记为成功，也不能因输出缺失删除已有经验。

## 7. 云见写入与有效性同步

### 7.1 字段映射

| 云见字段 | 规则 |
| --- | --- |
| scene | 测试脚本调测经验 |
| scene_id | 字符串 "421" |
| doc_id | 固定命名空间 + hash([group_id, fix_step_id]) |
| user_id | 源 test_user；空值为字符串 "0" |
| product.product_id | group_id 转字符串 |
| metadata.product | 接口返回的 product |
| title | 主语 + 核心失败表现 |
| summary | 失败、根因及修复摘要 |
| experience | 五段式 Markdown |
| rag_search_text | 结构化失败特征 + 失败现象 + 核心错误文本 |

metadata 同时保存 case_id、fix_step_id、related_step_ids、失败定位特征和提取版本。Debug Trace 保存真实源 test_user。

doc_id 不依赖大模型生成的标题或失败现象文本，也不依赖可补全的 test_user。同一修复点重跑保持稳定。原 user_id 非 "0" 时保留；原为 "0" 且源数据补全真实用户时更新。

### 7.2 共用现有写入逻辑

通过内部业务函数复用创建/覆盖流程，保留自动向量化、旧版归档、version 递增和质量检测，不直接调用 FastAPI 路由函数。

需要抽取时，API 和任务共同调用同一业务函数。任务入口必须显式完成或安排质量检测，不能依赖无人执行的 FastAPI BackgroundTasks 对象。

同一 doc_id 内容未变化时跳过写入。写入成功但 SQL 状态保存失败时，下次用稳定 doc_id 及源版本/内容摘要核对现有经验，避免不必要的重复覆盖和版本递增。

### 7.3 只保留有效经验

- 原有效修复被源数据明确改为无效：删除本任务对应 doc_id，并同步状态。
- 删除复用现有业务流程，保留系统已有历史归档；当前检索不再返回该经验。
- 完整输入及合法模型结果明确判定不具备有效关联证据时，移除对应旧经验并记录原因。
- 网络失败、模型超时、解析错误或结果漏项不能当作失效依据，保留状态并重试。
- 删除返回不存在，按幂等成功处理。
- 源记录物理删除只有接口能提供删除通知或完整性保证时才能同步；不根据分页未返回就推断删除。

## 8. 配置与试运行

| 配置 | 初版约定 |
| --- | --- |
| enabled | 默认关闭，配置完成后启用 |
| interval_days | 1；可配置 |
| timezone | Asia/Shanghai |
| range_start | 2026-08-01 00:00:00+08:00 |
| range_end | 2026-10-01 00:00:00+08:00 |
| page_size | 可配置 |
| success_fix_values | 按接口实际枚举配置“修复有效” |
| 增量/轨迹 URL、鉴权 | 接口交付后配置 |
| HTTP/LLM 超时、有限重试次数 | 可配置 |
| 模型名称、输入/输出预算 | 复用现有模型配置并预留预算 |

“8月—9月”按 2026 年 8、9 两个自然月解释，范围为左闭右开。执行当日只有已存在的数据可处理，不假定未来 9 月数据已存在。

该时间范围限制增量发现范围；被选中的组合仍读取完整历史轨迹作为上下文，仅写入范围内有效修复点对应经验。后续全量补跑使用相同 doc_id 保证不重复。

试运行通过 run_once 手动执行；验证通过再启用每日任务。初版以可配置执行间隔调度，不强行指定未经确认的凌晨执行时刻。

## 9. 最小验证与实施顺序

实施顺序：

1. 抽取或复用内部经验写入、删除函数，确认质量检测和版本行为一致。
2. 增加状态表、配置和两个数据接口适配；接口未交付时使用样例 Mock。
3. 实现轨迹处理及 Prompt，先完成 run_once。
4. 验证样例和重复执行，再注册每日任务。

必要验证：

- 一条轨迹多个修复点各生成一条经验，来源关联正确；
- 无有效修复正常跳过，同类现象不跨轨迹合并；
- 空用户查询使用源语义，云见 user_id 写 "0"；
- 相同修复点重跑不重复建文档，源内容更新覆盖原 doc_id；
- 失效删除与删除重试正确，模型故障不误删；
- 轨迹查询失败、写入失败和状态保存失败均可恢复；
- 游标推进后仍可找到并重试失败轨迹；
- 超长轨迹分批结果保持完整，不因缺失结果清理经验；
- 单实例任务无重叠，内部写入仍执行向量化、版本及质量检测。
