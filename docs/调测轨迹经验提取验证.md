## 2. 运行前配置

将以上文件合入完整 memory 工程，使用该服务已有的 Python 环境、公共模块、数据库连接、模型和 ES 配置。GitHub 上传的是部分工程，本地离线测试不能替代内网联调。

检查 `project_configs/settings.py` 中的 `TASK_RUNNER_CONFIG['TRACE_EXPERIENCE_EXTRACT']`：

| 配置 | 初始值及说明 |
|---|---|
| `enabled` | `False`；手动命令可在关闭状态下运行 |
| `interval_days` | `1`；每轮完成后等待一天，可搭配小时、分钟调整 |
| `job_name` | `trace_trial_202608_09`；更换试运行范围时使用新名称 |
| `range_start` / `range_end` | 北京时间 `2026-08-01 00:00:00` 至 `2026-10-01 00:00:00`，含开始、不含结束，按 `updateTime` 筛选修复点 |
| `source_url` | 已提供的 `scriptGenAgentTrajectory` 地址 |
| `source_method` | 默认 `POST`，请核对接口实际请求方式 |
| `headers_env` | 从 `TRACE_EXPERIENCE_SOURCE_HEADERS` 环境变量读取 JSON 格式请求头，按接口要求配置鉴权 |
| `verify_tls` | `True`；如内网使用自签证书，可通过 requests 的证书环境配置提供可信 CA |
| `page_size` | `100`；试跑可改为 `10` |
| `max_pages_per_run` | 每轮最多读取 `100` 页增量数据 |
| `retry_trace_limit` | 每轮先重试最多 `100` 条待处理或失败轨迹，优先处理等待更久的记录 |
| `model_name` | 复用已有模型名称，可修改 |
| `context_limit` | 必须填写模型实际上下文上限，初始为 `None`，未填写时任务会报错退出 |
| `max_output_tokens` / `safety_margin` | `10240` / `2048`；输入长度沿用现有 token 估算方法，需为所用模型留足余量 |
| `extraction_version` | `v1`；修改提取规则后可调整，已重新发现的轨迹会按新版本处理 |

历史查询仍读取该 `caseId + testUser` 的完整上下文。普通轨迹一次分析；超过模型预算时按修复过程拆批；单个修复过程仍过长则标记失败、保留已有经验。

在测试环境确认 ES Mapping 允许写入 `product.product_id` 以及任务使用的 `metadata` 字段。`product.product_id` 为字符串；若它是 `keyword`，保持默认过滤路径；若实际精确字段为 `.keyword`，设置环境变量：

```text
EXPERIENCE_PRODUCT_ID_FIELD=product.product_id.keyword
```

接口未返回 `product` 时不填写 `metadata.product`。返回后按实际值保存，届时需确认其类型与 ES Mapping 一致。

## 3. 手动试运行

以下命令在完整 memory 工程根目录执行。手动运行期间保持定时开关关闭，同一时间只运行一个任务进程。

首次创建两张任务状态表：

```bash
python -m memory_service.trace_experience_pipeline --init-tables
```

读取一页增量数据并处理对应完整轨迹：

```bash
python -m memory_service.trace_experience_pipeline --once --max-pages 1
```

`--max-pages` 只限制增量页数。为完整分析经验，该页涉及的轨迹仍会查询全部历史分页，并可能产生多条经验。

核对以下结果：

1. 日志输出 `trace experience summary`，包含发现、完成、失败、新建、更新、删除、跳过计数；这些是本轮操作次数。
2. SQL 表 `trace_experience_job_state` 保存增量游标，`trace_experience_record` 保存每组轨迹状态和经验对应关系。游标表示数据已可靠记录，失败轨迹仍会重试。
3. 云见经验 `scene_id` 为 `421`，场景为“测试脚本调测经验”；`product.product_id` 来自 `groupId`。
4. 一条轨迹有两次有效修复时，应分别生成经验；每条标题为“主语 + 失败现象”，正文有 Debug Trace、Error Log、Diff、Root Cause、Pattern。
5. `testUser` 为 null、空字符串或 `no user` 时，经验 `user_id` 为 `"0"`；历史查询保留原值，Debug Trace 记录原值。更新时保留原非零经验用户。
6. `success`、旧 `PASS` 可进入有效修复判断；没有实际修改的记录不会调用提取模型。`executeResult` 不替代修复结果。
7. 再次运行时，相同修复点的 `doc_id` 保持一致，已完成且内容未变的提取结果会复用。注意下一轮会继续读取后续增量页，出现其他新经验属于正常情况。
8. 使用测试数据将修复结果改为 `fail` / `FAIL` 并同步更新 `updateTime` 后，下轮撤销对应经验。日志不足、模型输出不完整、接口失败时应保留已有经验，并在 SQL 状态中区分跳过或失败。

确认后将 `enabled` 改为 `True` 并重启原服务，任务随 `task_runner.py` 启动。关闭开关并重启可停止后续定时提取。

放开历史范围时使用新的 `job_name`：`range_start` 填实际起始时间，`range_end` 可设为 `None`。固定经验 ID 可避免与试运行结果重复创建。仅修改版本号不会主动扫描已完成的全部轨迹；需要全量重提取时也应使用新 `job_name`。
